The brief: what you're building

read this first

A game in the Python Arcade (pygame). The player moves around a level and touches objects. Some give points, some take hearts, some open things, some chase you. The game ends in a win or a loss. Every game you've built this year was state plus rules that change the state. This time there's one new rule, and it's the whole project:

# THE ONE RULE: nothing touches state directly. Every change goes through change(). def change(state, key, new, cause): old = state[key] state[key] = new LOG.append({"t": now(), "key": key, "old": old, "new": new, "cause": cause}) # a coin: change(state, "score", state["score"] + 10, "coin#4") # spikes: change(state, "hearts", state["hearts"] - 1, "spikes#2") # winning: change(state, "status", "won", "flag")

The LOG is your black box: a list of records, which makes it a table (Data Vault, Stat Check). It saves with the game. And it has a test: replay(new_game(), LOG) must rebuild your final state exactly. If any rule changes state without going through change(), the replay drifts and the test fails. If it isn't in the log, it didn't happen.

Stop 3 · The objects table

Stat Check: rules read columns

Every object in your game is one row. The columns are what the rule reads. Your touch() rule will never say "if it's a coin": it reads points and hearts from the row and applies them. Adding a new object later should mean adding a row, not new code.

KindLooks likePointsHeartsRemoved on touch?Moves?Other effect

Points and hearts can be negative. "Other effect" is for anything the columns don't cover: opens a door, teleports, saves the game, speeds you up. If more than one object needs the same other effect, that's a new column.

Done whenat least 4 kinds. At least one gives something, one takes something, one moves, and one is the goal.
