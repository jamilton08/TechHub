Stat Check: every game is a database

In Save Point you learned that a game is state plus rules. Now look closer: every game you've played is really a database. The stages are rows in a table. The monsters' stats are columns. The rules are queries that read those rows and change the save data. You'll play a small RPG while watching every read and write it makes, then build your own monsters and stages, change the rules in Python, query the game like a database, and fix two real bugs.

    Stop 1 of 6 · 10 points

    Stages, stats and rules

    This is Moss Keep, a tiny RPG. Play it and keep one eye on the database panel (next to the game, or under it on a phone). Every click runs rules, and between them they do the four things a database does: read rows, update them, insert new ones and delete old ones.

    STAGES

    Each level is one row: a name, a lineup of monster ids, the level you need. A new stage is a new row, not new code.

    stats

    Numbers in columns: hp, atk, def, spd, xp, gold. Every monster has the same columns with different numbers.

    rules

    Small Python functions. damage() reads atk and def. It never asks which monster it is, so one rule works for all of them.

    state

    The save data: tables the rules change as you play (you, the foes in this fight, your bag, which stages you've cleared).

    you click Attack→attack(state)→rules read stats→rules write state→screen redrawn from state↺

      This is Moss Keep's game data. Make it yours: change the stats, invent a monster, and drag monsters into stages (or use the Add a foe menu on each stage).       MONSTERS one row per kind of monster

      Drag a monster by its picture into a stage. HP hit points · ATK attack · DEF blocks that much of each hit · SPD faster hits first · XP and Gold you earn.

      STAGES one row per stage, in order. Stage ids are 1, 2, 3… and can_enter uses them to find the stage before.

      Your tables need

        You haven't written a single line of code, and the game already knows how to fight your new monster. The rules only read stats, never names. That's why games keep this stuff in tables: designers add content and balance it by changing numbers, and programmers don't have to touch the rules.

          Query the game

          A game asks its data questions all the time: which stages are open, which monsters are left, what's the strongest item you can afford. Asking a database a question is called a query. Python and SQL are two ways to write the same query.

          The recipe every game follows
          
          
          
            
          game data
          tables that ship with the game: stages, monster stats, items. Rules read them. Players can't change them.
          
            
          save data
          state: tables the rules change while you play. This is what a save file (or a game server's database) holds.
          
            
          don't store
          anything you can work out from the rest, like a total or an average. Compute it when you need it.
          
            
          rules
          functions that read stats and write state. They name columns, never specific monsters.
          
            
          CRUD
          every write is an INSERT (create), UPDATE or DELETE. Every read is a SELECT.
